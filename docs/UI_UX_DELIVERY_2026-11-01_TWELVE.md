## Транспорт и совместимость / developer handoff

Clients opt into `X-Smena-Whiteboards: demand`. Workspace responses contain metadata-only `whiteboards[]`, no legacy `project.whiteboard` bodies, and a `whiteboardCatalog` envelope with hashes, counts and bounded geometry-only thumbnails. Material titles and text are never copied into thumbnail metadata.

`GET /api/whiteboards/:id/content?revision=…` checks current workspace/project access and returns a version-checked body. Hidden boards return 404. Session/workspace changes invalidate body caches; caches retain at most three bodies. Opening a board applies an external canonical snapshot only after outstanding synchronization has finished. Failure leaves a retry screen, not an editable empty canvas.

On writes, unchanged/unloaded bodies are omitted. `restoreWhiteboardBodies` fills only existing identities from the current locked canonical state before the existing ACL/author/association/history checks. Unknown new documents must include valid content. Revision, restore-token and replacement-hash checks remain. Optimized file-write paths expand their comparison against current core metadata; ordinary writes do not trust the shortened authorization snapshot as a content source.

`GET /api/whiteboards/search` performs bounded full-text matching on the server and returns metadata-only results after current access projection. Shared search/palette can find cards whose bodies are not loaded locally. Catalog filters, sort and return scroll are device-local and scoped by user/workspace, consistent with other catalogue preferences.

The canonical Google Drive/local aggregate and compatibility aliases are intentionally retained for older clients and complete backups. This step separates network loading and partial writes; it does **not** claim independent physical Drive body shards, removal of old aliases, a larger aggregate storage limit, or elimination of every server-side cold aggregate read. A future physical migration must retain the same backup and access contracts.
