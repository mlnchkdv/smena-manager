Незатронутые части не загружаются. `file-removal-patch.js` допускает браузерное удаление только при точном совпадении всех остальных core-полей и валидных trash-записей; смешанные изменения и relation-sensitive случаи возвращают полный canonical fallback. Новая физическая загрузка может прочитать только core/выбранную insertion-часть; существующий физический ID или отсутствие индекса требуют полного пути для проверки дубликатов. Частичный снимок инвалидирует полный кеш, но никогда его не заменяет.

`createColdDatabaseBackup` + `withCatalogBackupSpool` читают свежий root и **все** immutable-части с SHA-256/identity/accounting-проверками в приватный временный JSONL-spool. До завершения проверки upload копии не начинается. Два ограниченных массива offset/length позволяют передать полные записи в исходном глобальном порядке без полного массива файлов/clone в heap; файл и временный каталог убираются в `finally`, включая ошибки. Сохраняются самостоятельный JSON-envelope, история и registry; бинарные байты вложений остаются отдельными объектами. Это уменьшает память, **не** обязательное чтение всех частей; root/index/registry, временный диск и локальные синхронные чтения остаются затратами. Restore/import safety checkpoints и несовместимые/миграционные корни используют полный canonical-путь. Нельзя удалять свежий proxy-upload при неопределённом исходе публикации: root мог уже сохраниться; сейчас объект сохраняется с диагностикой. Отдельная безопасная reconciliation orphan-объектов ещё нужна.

**EN.** Earlier dated descriptions of full add/remove reads and cold-backup materialization now describe fallback, not every operation. Optional validated `_fileCatalog.physicalReferences` stores physical-identity counts consistent with accounting/registry; canonical writers publish it atomically, without read-time migration. Internal trusted `mutateWorkspaceCatalogCommand` handles verified new uploads and recoverable removals of up to 500 files. Fresh stored-member/project ACLs precede selected-part reads; private snapshots bind root, ETag and verified rows. Target checks, lease ownership, exact byte accounting, order, aliases/retention and root CAS remain enforced; unrelated parts stay unread. `file-removal-patch.js` classifies browser removals only when all other core fields and exact trash records match. Mixed/relation-sensitive changes, duplicates, missing indexes and migrations keep canonical fallback. Partial snapshots invalidate, never replace, the complete cache.

Cold standalone copies verify every immutable part into a private temporary JSONL spool before starting the backup upload. Bounded offset/length arrays reconstruct the original global record order without a complete file array/clone in heap; cleanup runs on success and failure. Full JSON metadata/history/registry remain self-contained, but binary attachments remain separate. This saves heap, not mandatory integrity I/O, root/index/registry cost, temporary disk or synchronous local-read overhead. Recovery checkpoints and incompatible/migrating roots keep full fallback. Ambiguous proxy publication no longer eagerly deletes uploaded content, because the root may already reference it; safe delayed orphan reconciliation is still outstanding.

## 1. Русская версия

### 1.1. Что это за проект

Smena Manager — веб-приложение для совместной работы команды: задачи, проекты, команды, календарь, хронология, входящие, уведомления, файлы, база знаний, закладки и граф связей между материалами.

Основной production-адрес: **https://smena-manager.vercel.app/**.

Проект создавался как собственный командный таск-менеджер на базе подхода KMS-brain. PostgreSQL намеренно не используется. Общие данные хранятся в JSON-документах Google Drive, а бинарные вложения — отдельными объектами Drive. Это решение подходит небольшой команде и сохраняет независимость от отдельного сервера базы данных.

Поддерживаются русский и английский языки. Внутренние ключи интерфейса остаются стабильными английскими строками, а отображение локализуется слоем `src/core/i18n.js`. Пользовательские названия, описания, теги, имена команд и другие данные нельзя пропускать через переводчик интерфейса.

### 1.2. Технологический стек

- Frontend: plain JavaScript ES modules, HTML templates и CSS; UI-фреймворк не используется.
- Сборка: Vite 6.
- Backend: Express в `src/server/app.js`, локально запускается Node.js, на Vercel — `api/index.js`.
- Хранилище production: Google Drive API, версия JSON и ETag используются для условной записи.
- Координация конкурентных записей: Redis lock через `REDIS_URL` или прямой Drive-режим с ревизиями/ETag (`WORKSPACE_WRITE_MODE=drive`).
- Авторизация: Google Sign-In для подтверждённых email из whitelist; локально и аварийно — Access ID.
- Email: Gmail API через отдельный refresh token `GMAIL_OAUTH_REFRESH_TOKEN`.
- Push: Web Push с VAPID-ключами.
- Граф: Cytoscape.js, lazy-loaded chunk.
- PDF: self-hosted PDF.js без выполнения скриптов документа.
- Тесты: Node test runner для server/unit-проверок и Playwright для браузерных сценариев.

Требуемая версия Node.js — **22.x** (`.nvmrc`).

### 1.4. Модель данных и хранение

Канонический workspace — JSON-снимок с ревизией. Core-коллекции включают проекты, задачи, участников, команды, события, уведомления, файлы, связи и корзину. Большие коллекции вынесены в логические документы:

- `workspace` — core;
- `knowledge` — `knowledgeNotes` и `knowledgeFolders`;
- `bookmarks` — закладки и папки закладок.

Документы имеют независимые ревизии. В schema v3 core, знания и закладки остаются в основном JSON Google Drive; полный каталог файлов вынесен в неизменяемые части по проектам, указатели и компактный индекс находятся в root. Единая ETag-защищённая запись root атомарно публикует все изменения. Старые schema-v2 aggregate и отдельные файлы документов поддерживаются для чтения/миграции; отдельные документы не являются source of truth после первой aggregate-записи.

Ограничения:

- транспорт каждого логического документа — до 4 MiB;
- это ограничение JSON, а не бинарных файлов;
- вложения по умолчанию — до 100 MiB (`SHARED_FILE_MAX_BYTES` может менять лимит);
- Vercel не используется как постоянная файловая система;
- `localStorage`/IndexedDB — только offline cache и owner-scoped recovery drafts, не общий источник правды.

Production Drive-структура содержит основной JSON, отдельные объекты вложений, приватные файлы с auth sessions, push subscriptions и delivery diagnostics, а также папку резервных копий. Конкретные ID и секреты берутся из Vercel Environment Variables и не коммитятся.

### 1.5. Авторизация, роли и безопасность

Google Sign-In принимает только verified email, который совпадает с активным профилем из `ACCESS_IDS_JSON`. Сессия подписывается `SESSION_SECRET`, хранится в HttpOnly cookie и действует семь дней. Access ID — аварийный/local fallback, в production по умолчанию выключен.

Роли:

- `admin` — участники, команды, настройки, резервные копии, восстановление, все shared-изменения;
- `editor` — задачи, проекты, файлы, знания, закладки и связи в разрешённых проектах; не может менять membership и workspace settings;
- `viewer` — чтение и личные настройки, без shared-записи.

Проверки выполняются на клиенте и сервере. Сервер не доверяет роли, member ID или email из тела запроса. Входящий session context и `X-Smena-Account` сверяются с текущей сессией. Private project endpoints удаляются из workspace projection и графа.

Основные security-механизмы: security headers в `vercel.json`, CSP, HttpOnly cookies, rate limit входа, request ID (`X-Request-ID`), отсутствие provider secrets в логах, строгая валидация workspace schema, отказ от небезопасных файлов и sanitization rich text/HTML.

### 1.6. Синхронизация и исправление гонки

Клиентские sync-объекты находятся в `src/core/workspace-sync.js`. Они отслеживают подтверждённый snapshot, pending draft, активную запись, ревизию, конфликт и retry backoff. Draft journal позволяет восстановить несохранённые изменения после перезагрузки.

Главные правила:

1. Запись проходит только с ожидаемой ревизией.
2. Сервер отклоняет stale revision (`409 REVISION_CONFLICT`) и не перезаписывает новые данные.
3. На Vercel Redis lock предпочтителен при высокой конкуренции.
4. В direct Drive mode запись защищена ETag и серверной очередью.
5. На клиенте все записи общего workspace и knowledge/bookmarks проходят через `serializeWorkspaceWrite` в `src/shared/workspace-documents.js`.
6. При конфликте приложение не делает silent overwrite: локальная версия сохраняется, пользователь видит recovery dialog и может скачать локальную копию, принять серверную версию или продолжить с явным решением.

После изменений, затрагивающих shared state, нужно проверять как минимум: два быстрых изменения подряд, reload, вторую вкладку и stale revision. Нельзя добавлять fire-and-forget запись, которая обходит очередь.

### 1.7. Разделы и функциональность

**Задачи и проекты.** Поддерживаются list/board/table/calendar/timeline, приоритеты, сроки, исполнители, повторения, подзадачи, зависимости, milestones, файлы, комментарии, реакции и упоминания.

**Входящие и уведомления.** Входящие фильтруют mentions, assignments, comments, deadlines и другие события. Уведомления принадлежат конкретному получателю. Broad mention не уведомляет автора автоматически, а explicit self-mention поддерживается. Outbox, retries, email и push работают независимо.

**Файлы.** Браузер получает resumable upload ticket, на Vercel загружает 8 MiB chunks прямо в Drive, затем сервер проверяет размер, marker, folder и регистрирует metadata. Файлы имеют стабильную storage identity; имя не используется как единственный идентификатор. Изображения, текст и PDF имеют ограниченные previews; активные/неизвестные форматы скачиваются безопасно.

В рабочем разделе и вкладке проекта загрузка доступна настоящей кнопкой с клавиатуры (`chooseStoredFiles`), а не только подписью скрытого поля. Мобильный список показывает поля на всю ширину карточки, локализует подписи и оставляет меню рядом с названием. Поиск учитывает исходное и локализованное название типа файла; видны количество результатов, очистка запроса и сброс всех фильтров с возвратом фокуса. Компактная панель на телефоне использует две колонки фильтров; container query учитывает доступную ширину после бокового меню. Права по-прежнему проверяет сервер; расположение/имя физического файла не меняется от этих UI-операций.

В разделе «Файлы» доступны логические папки проекта (`project.fileFolders`) с вложенностью, поиском, хлебными крошками, ограниченными страницами и восстанавливаемым архивом пустых папок. `file.folderId` и соответствующее поле вложения задачи указывают только на активную папку того же проекта; загрузка в текущую папку передаёт folderId через proxy и подписанный direct-upload ticket. Перемещение не меняет storage identity, физическую папку Drive или ACL. В одном проекте допускается до 2000 папок, глубина до 32 уровней, названия 1–120 символов; одинаковые активные названия в одной родительской папке запрещены. При восстановлении файла с недоступной исходной папкой он попадает в корень проекта.

Загрузка, переименование, папки и перенос требуют права редактирования проекта. Удаление чужого файла дополнительно требует роли администратора; просмотр/комментирование не даёт файловых write-действий. Массовый выбор работает в плитке/списке и сохраняется при фильтрации, но очищается при смене пользователя/пространства; лимит 500 файлов. Перенос разрешён внутри одного проекта, удаление — в восстанавливаемую корзину с подтверждением списка и Undo. Весь набор заново проверяется до первой мутации, вложения задач обновляются по стабильным ID. Папки показываются по 4 на телефоне/8 на широком экране; выбор назначения — по 20 с поиском. Это организация внутри приложения, не произвольный файловый менеджер всего Google Drive.

Файловый поиск и счётчики папок используют `createFileIndex`, построенный на актуальном снимке, без кэша, который мог бы пережить изменение прав/синхронизацию. Запрос разбивается на слова, не зависит от регистра и различия е/ё. Вид плитка/список, сортировка, 25/50/100 файлов на странице, компактные/плиточные папки и сворачивание сохраняются в `smena.files.ui.v1` отдельно для пары пользователь/пространство в текущем браузере. Текущее выделение и поиск не сохраняются автоматически; пользователь может явно сохранить до 12 именованных наборов фильтров в отдельном device-local ключе `:filters`. Набор включает проект, папку, запрос, тип, сортировку и рекурсивный режим; недоступные назначения не подменяются общим списком. Компактные папки показываются по 8 на телефоне/16 на широком экране; обычные плитки — по 4/8. Можно перейти по номеру страницы папок/файлов через Enter.

Рабочий раздел и вкладка файлов проекта используют один `pageFiles(projectId)`; проектный контекст закрепляет область данных и доступные upload targets. Действия/диалоги файлов загружаются вместе с соответствующей страницей, в том числе при прямом входе во вкладку проекта. Перенос папки показывает число вложенных папок/файлов и до мутации проверяет циклы, глубину, совпадения имён и права; вся ветка остаётся в том же проекте, `file.folderId` и storage identity не меняются. По умолчанию внутри папки показаны только прямые файлы, «Включить вложенные папки» явно расширяет выдачу. «Выбрать страницу» и «Выбрать найденное» — разные действия; выбор всей выдачи отключается сверх 500 файлов.

Клиент запрашивает `X-Smena-File-Catalog: demand`: начальный core-снимок не содержит полного массива файлов и не запускает загрузку каталога. POST `/api/files/catalog/query` возвращает 25/50/100 ID, точные итоги, до 32 счётчиков папок и до 500 ID найденного для явного массового выбора. POST `/api/files/catalog/resolve` разрешает до 100 ID за запрос с проверкой ревизии/ACL и лимитом страницы 2 MiB; клиент дочитывает продолжение большой страницы. В `D().files` находятся только нужные записи и выделенные файлы. PUT передаёт `fileChanges`: вытеснение страницы из кэша не означает удаление; удаление отдельного файла подтверждается новой командой корзины, каскады задач/проектов достраиваются сервером с полными файлами в восстанавливаемой корзине. Прямой URL файла, загрузки, вложения, поиск и связи разрешают нужные ID по запросу. Каталог ограничен 32 MiB, core/document transport — 4 MiB; вложения задач и корзина пока входят в core. Старый режим `pages` сохранён для совместимости.

Массовое скачивание создаёт ZIP в браузере из явно выбранных файлов: до 100 файлов и 50 MiB исходных данных, независимо от лимита выделения 500 для переноса/корзины. `file-download.js` и ZIP-библиотека `fflate` загружаются по требованию. Данные последовательно читаются через существующий авторизованный `/api/files/:id/content`; на сервере не создаётся архив или временная папка, данные не отправляются стороннему ZIP-сервису. `ZipPassThrough` не сжимает уже сжатые форматы повторно. Сохраняются пути проекта/папок; Unicode, конфликтующие имена без учёта регистра, небезопасные пути и зарезервированные имена обрабатываются при экспорте без переименования оригиналов. Есть прогресс и отмена; ошибка чтения, превышение фактического размера или смена пользователя/пространства отменяют публикацию результата целиком. Старые записи без сохранённого содержимого в ZIP не включаются: пользователь должен убрать их из выделения. Лимиты проверяются до запроса и при чтении потока, включая нулевой оставшийся бюджет. Proxy upload сохраняет UTF-8-имена отдельно от legacy Latin-1-декодирования multipart.

Отдельная кнопка «ZIP потоком» отправляет same-origin form POST `/api/files/archive?account=...` с HttpOnly cookie и проверкой аккаунта. Загрузка идёт в контексте браузера, не заменяя страницу приложения; собственный прогресс приложения относится только к браузерному ZIP. Сервер использует `ZipPassThrough`, части до 64 KiB и backpressure без полного буфера файла/архива. Ограничения: 500 файлов, 250 MiB фактических исходных данных, 45 секунд (Vercel function настроена на 60). Перед очередным файлом заново проверяются актуальная роль, membership, проект и storage identity. Обрыв/таймаут уничтожает поток; архив не сохраняется в Drive. Ограничение одновременно работающих экспортов действует только внутри экземпляра функции: один на аккаунт и до восьми всего, с истекающей lease. Это не распределённая квота и не возобновляемая фоновая задача. Реальное поведение загрузок при блокировке телефона/уходе приложения в фон требует физических iOS/Android-проверок.

Готовый браузерный ZIP остаётся доступен по явной ссылке «Сохранить ZIP» до пяти минут: браузер может подавить автоматическое повторное скачивание после асинхронной подготовки. Повторное нажатие не читает Drive заново. Blob URL освобождается при закрытии, замене, истечении срока или недействительном account/workspace/ACL-контексте. Не объявляйте автоматический клик доказательством доставки файла; проверяйте сам скачанный архив. Панель готового результата не блокирует последующий экспорт.

«Возобновляемый экспорт» — отдельный протокол `/api/files/exports`: скрытые задания сохраняются в Drive вместе с aggregate, неизменяемые части по 4 MiB — как файлы Drive. Ограничения: 500 файлов/1 GiB, 24 часа, до 16 живых заданий и четырёх на пользователя, до четырёх активных worker leases; один незавершённый экспорт на пользователя. ETag/revision-проверки и fencing-token не дают устаревшему worker опубликовать checkpoint. Staging фиксируется до загрузки части; неизвестный результат загрузки находится по имени и проверяется SHA-256 перед повтором. Проверяются версия источника, размер, текущие ACL, SHA-256 частей и ZIP CRC. Готовый результат отдаётся потоком с детерминированным ETag и HTTP Range; целый архив не буферизуется. Продолжение подготовки инициирует активная вкладка: закрытие/фон приостанавливают её до возобновления, автономной очереди нет. Задания имеют отдельный лимит метаданных 8 MiB; части учитываются в штатном реестре/отложенном GC, живые задания защищают их от очистки.

Google Drive хранит schema-3 root с `_fileCatalog` manifest v3 и неизменяемые JSON-части по проектам (до 2000 записей/2 MiB). Manifest содержит ID частей, SHA-256, размеры и компактный индекс ID/папок/размеров/задач, но не полные записи файлов. Auth/core читают root без частей; запрос проекта/ID сначала определяет доступные проекты, затем читает только подходящие части. Общий поиск/сортировка читают разрешённые части на сервере, возвращая клиенту ограниченную страницу. Поисковая проекция отбрасывает историю и реквизиты хранения после проверки исходной записи; LRU проверенных неизменяемых частей ограничен 8 MiB UTF-8. Холодный глобальный запрос ещё требует обхода доступных частей. Полные записи и резервные копии материализуются перед существующими общими валидациями/транзакциями, но граф и выбор связей используют отдельные ограниченные read models, описанные ниже. Все части проверяются, неизменённые переиспользуются; root публикуется последним через If-Match. Перед первым переходом создаётся полная копия. Старые aggregate/v1/v2 читаются; неподдерживаемая схема/manifest закрывают старым серверам запись. Операторский `node scripts/file-catalog-layout.js --inspect` ничего не меняет; смена формата требует `--layout=aggregate|project-shards --revision=N --confirm`, создаёт копию актуального состояния и сохраняет schema 3/новые правки. Не восстанавливайте для отката старую копию миграции. Старые/неопубликованные части пока не удаляются автоматически. Настройки переноса показывают фактический формат и число частей; лимиты/счётчики процессов остаются независимыми. Наборы фильтров — device-local; обновление приложения только явное после проверки сохранения/форм/передач. Порядок записей хранится в manifest; содержимое частей сортируется по стабильному ID, поэтому изменение общего порядка не переписывает части других проектов. Перед чтением повторно проверяется актуальная роль участника; скачивание содержимого разрешает только нужный файл.

**Дополнение по холодному поиску — 24 октября 2026.** Manifest v3 теперь допускает производный `part.search: {version: 1, id, sha256, bytes}`. Индексная часть содержит только `fileCatalogIndex`, без истории/физических реквизитов хранения; если полная часть уже состоит только из таких полей, используются те же байты/ID. Поиск/граф читают компактные части, проверяя SHA-256, размеры, порядок, project и identity/folder/size/task-ключи root. Свежие права проверяются до чтения частей, кэш их не обходит. Это индекс метаданных, не инвертированный full-text индекс: холодный общий запрос по-прежнему сканирует разрешённые индексные части. При отсутствии `search` остаётся проверяемый fallback на полные записи. Индекс публикуется последним вместе с root при следующей штатной записи; чтение не запускает скрытую миграцию. Изменение только истории переиспользует неизменившийся индекс. Старые v3-серверы могут отбросить производный указатель при записи без потери исходных файлов.

Служебные чтения: список/результат/проверка возобновляемого экспорта разрешают ID только живых собственных заданий из того же root; без таких заданий части не читаются. Нативный ZIP читает выбранные ID и повторно проверяет нужный файл перед передачей. Проверки версии/размера/storage identity и актуальной роли сохранены. Полные записи также используют проверенный LRU. Поиск базы знаний, outbox-диагностика и разрешение участника для push/test не читают каталог; GET preferences переиспользует приватный снимок текущего auth-middleware, возвращая только настройки своего участника. Снимки чтения нельзя сохранять как canonical workspace. Общие mutations и backup/restore пока материализуют все файлы.

Подробная ёмкость использует необязательную `_fileCatalog.accounting` v1: ревизия, точные UTF-8-байты envelope `{data:{files},revision}` и результат `fileStorageAccounting` по полным данным. Сводка пересчитывается при каждой штатной записи, включая изменения только trash/GC/registry; в root публикуется атомарно с указателями частей. `loadDatabaseStatus` читает свежий root, проверяет структуру/ревизию/счётчики, не скачивает части и не создаёт даже массив файловых заглушек. Статус не заменяет canonical write baseline; layout, документы и показатели связаны с тем же root. `catalogAccounting: {source: 'manifest'|'canonical', revision}` в `/api/storage/status` указывает фактический путь. Старые root без сводки точно материализуются, чтение не мигрирует данные. Повреждённая/неподдерживаемая сводка вызывает явную ошибку, а не нули. Состояние не берётся из устаревшего worker-cache. Алиасы, неизвестные размеры и удерживаемые физические объекты считаются как прежде; объём backup-only объектов остаётся `null`, это не полный учёт всего Drive. В UI неизвестные размеры показаны отдельно для логических записей, активных и удерживаемых объектов, без суммирования пересекающихся категорий. Размеры root и проверка его manifest всё ещё растут с каталогом; сводка не устраняет эти ограничения.

`getWorkspaceDatabase({fields})` передаёт `identities: false` в `loadDatabaseCore`, если `files` не запрошены: auth/служебные поля не создают файловых заглушек. Обычный core и явный запрос `files` сохраняют индекс ID. Учёт по root не является полной проверкой наличия/контрольных сумм каждой части и бинарного объекта; эти проверки остаются на фактическом чтении и операциях восстановления.

Сохранение core с `fileChanges` реконструирует каталог, применяет каскады и проверяет ACL внутри `mutateWorkspaceDatabase` по одному canonical-снимку; отдельного полного чтения до границы записи нет. Импорт, восстановление и удаление пространства используют тот же полный снимок для защитной копии, не загружая его повторно. `backupLabel` в опциях внутренней мутации создаёт копию после проверки/валидации и до CAS-публикации; сбой копии останавливает запись, а ownership Redis проверяется снова после неё. Импорт сохраняет ID своей копии в истории. Самостоятельная копия на Vercel всегда перечитывает актуальный canonical root, не используя двухсекундный UI-кеш. Для этих операций одна полная загрузка/валидация и полные файлы/документы в backup остаются обязательными.

Исключение — `mutateWorkspaceMetadata`: документы knowledge/bookmarks и настройки пользователя с `X-Smena-File-Catalog: demand` сохраняются root-only, без загрузки частей. `loadDatabaseMetadata` возвращает снимок без файлов, связанный через приватный WeakMap с исходным root, ID и ETag; нормализация проверяется на отсутствие побочных изменений. Изменять разрешено только выбранный документ с его независимой ревизией либо личные поля/настройки/read-state конкретного участника. Файлы, задачи, проекты, ACL, связи, реестр, корзина, GC и соседние документы неизменны. Используются та же граница локальной очереди/Redis lock, проверка ownership и If-Match именно прочитанного снимка. Лимиты core/документов проверяются обычным способом; точные байты каталога пересчитываются из revision-bound accounting с учётом роста числа цифр ревизии, физические счётчики и указатели частей сохраняются. Ответ настроек содержит identity-only индекс лишь для штатной ACL-проекции и demand-гидратации; глобальный canonical-кеш инвалидируется, частичный снимок туда не помещается. Старый root, отсутствие accounting или побочные миграции возвращают полный путь; повреждённые manifest/accounting и отсутствие ETag закрывают запись. Legacy-клиенты настроек сохраняют полный ответ. Это узкий copy-on-write root, **не** транзакции по отдельным проектам: скрытые повреждения неизменённых частей не перечитываются при такой записи, их SHA-256 и идентичности проверяются при фактическом чтении; backup/restore и файловые изменения материализуют полный каталог.

Обновление 24.10: ещё одно узкое исключение — `tryMutateWorkspaceFiles` для demand-запросов: переименование/перенос между папками до 500 существующих файлов. Свежий root проверяется и нормализуется без побочных изменений; роль берётся из текущего участника, ACL проверяется **до** загрузки частей. Каждый входящий core-field должен совпадать с ACL-проекцией этого же root (с учётом текущего `me` и только folderId затронутых вложений задач). Прочитываются целиком лишь части с выбранными ID, с проверкой SHA-256/размера/идентичностей. Разрешены только name/folderId и type декоративного файла без physical identity. `loadDatabaseFilePatch` приватно связывает snapshot с root/ETag/проверенными строками; `saveDatabaseFilePatch` сохраняет незатронутые указатели, глобальный порядок, registry/retention/physical accounting и точно пересчитывает catalogBytes. При росте части она разделяется штатным writer. Ownership проверяется при staging и непосредственно перед CAS root; частичный снимок никогда не попадает в полный worker-cache. Дополнительные core-изменения, добавления/удаления/дубликаты, физические изменения и миграции используют полный canonical-путь. Неизменённые части не сканируются повторно — это не полная проверка целостности всего Drive и не транзакции отдельных проектов.

Обновление backup: самостоятельная копия всегда читает свежий root, но `loadDatabaseForBackup` может подтвердить точный ETag уже полного canonical worker-снимка и не перечитывать части. Сохраняется именно захваченный до await снимок, а не новая глобальная переменная. Несовпадающий/отсутствующий ETag, холодный worker или изменённый root требуют полной материализации и проверки частей. Файл копии остаётся независимым полным JSON с историей/реестром; `backupJson` передаёт массивы по записям, без дополнительной большой JSON-строки. Бинарные вложения по-прежнему отдельные объекты, обычная JSON-копия не является независимым архивом их байтов. Старый aggregate поддерживается. Более ранние утверждения об обязательном полном перечитывании всех файловых изменений/самостоятельных копий относятся к общему fallback-пути, а не этим узким исключениям.

Подтверждённые команды `mutate` сразу вызывают `flushLocalSave` после permission guard, а не ждут 150-миллисекундного debounce; обычные формы сохраняют прежнее объединение ввода. В E2E сохранение проверяется ответом PUT с конкретной задачей, затем обновлением страницы. Responsive sweep разделён на четыре независимых viewport-теста с прежним лимитом 360 секунд на тест, покрытие всех 140 пар route/viewport сохранено. Для `workspace-smoke.spec.js` запись видео/DOM-trace включается на первом повторе; screenshot при ошибке остаётся всегда, полный первый trace можно включить через `--trace retain-on-failure`. Настройка recording должна находиться на верхнем уровне файла, не внутри `describe` (Playwright worker-scoped option).

В «Переносе данных» основные лимиты остаются видимыми, технический учёт раскрывается в «Подробностях хранения». На ширине до 1100 px навигация настроек горизонтальная; выбранный пункт прокручивается в видимую область также после resize. Служебные названия копий локализуются без переименования объектов Drive; пользовательские названия сохраняются. Ручные копии автоматически не удаляются, восстановление не удаляет выбранную копию.

**База знаний.** Заметки и папки поддерживают Markdown, tags, summary, category и `[[wiki links]]`. Неоднозначные wiki-ссылки не угадываются; target выбирается явно. Переименование заметки сохраняет stable target ID.

Новые файловые импорты сохраняют `sourceFormat: 'markdown' | 'text'` как признак происхождения. `formatted_markdown` остаётся полным исходником, включая YAML/frontmatter. `knowledgeDisplayParts` отделяет подтверждённый начальный блок метаданных только для отображения: чтение, карточки, предпросмотр редактора и история не показывают его в основном тексте, но дают сворачиваемый блок «Метаданные исходника». TXT с явным `sourceFormat: 'text'` никогда не очищается от похожих строк. Для старых заметок без признака формата применяется консервативное совпадение с сохранёнными полями или удержанной версией с тем же блоком метаданных. Исторический предпросмотр учитывает текущую заметку и пять её версий; чужой/изменённый блок не подтверждает происхождение. При реальном редактировании распознанного старого MD признак `sourceFormat` закрепляется до изменения полей, поэтому удаление старых версий не возвращает YAML в чтение. Чтение не мигрирует данные; неоднозначный/незакрытый блок остаётся обычным текстом. Поиск по исходным полям сохраняется, экспорт не удаляет метаданные, массовая миграция рабочих данных не выполняется.

Отображение папок справа переключается между `block` («Отдельный блок») и `inline` («Вместе с заметками»). В `inline` папки и заметки занимают общую адаптивную сетку; сохраняются меню папок, ограниченная постраничная выборка, поиск подпапок и перенос заметок. Скрытие папок независимо от режима. `folderLayout` хранится в локальных настройках пользователя/пространства (`smena.knowledge.ui.v1`), не в общей базе и не между устройствами. Начальная отрисовка и ввод в редактор используют один `knowledgeLivePreview`; динамический результат переводится отдельно, а пользовательский Markdown остаётся `translate="no"`.

На мобильном экране в общей сетке папки стоят в две колонки, заметки остаются полноширинными; названия папок переносятся максимум на две строки с полным именем в тексте/title. Карточка папки использует вертикальный flex, чтобы меню и кнопка переноса не выходили за её границы. `focusKnowledgeNotes` доступен в обоих режимах при наличии видимых заметок: переводит фокус и прокрутку к первой карточке без открытия редактора и без записи данных.

Переключение страницы папок возвращает фокус к первой папке новой страницы и прокручивает её в видимую область, в том числе на последней странице с отключённой кнопкой «Далее». Заголовки карточек заметок занимают до двух строк; полное название доступно через `title`, дата вынесена ниже названия, а метаданные выровнены по нижнему краю карточек одного ряда. В общей сетке иконки папок привязаны к верхнему краю и не смещаются из-за разной длины названий. Эти правила действуют без изменения содержимого заметок.

**Закладки.** Закладки имеют URL, описание, теги, папки, архив и связи. Архивная выборка сохраняется при редактировании, stale concurrent edit не воскрешает удалённую закладку.

**Граф.** Узлы имеют typed keys `note:<id>`, `bookmark:<id>`, `file:<id>`, `project:<id>`, `task:<id>`. Manual relations хранятся в `relations` с tombstone deletion. Автоматические project/task/file associations и wiki links вычисляются, не дублируются в shared state. Граф поддерживает фильтры, поиск, connected-only, archive, depth 1/2, selection, local graph, JSON export и list alternative. Визуальное окно ограничено 250 узлами; export получает весь разрешённый filtered set. Для плотного графа (>80 узлов или >160 рёбер) на дальнем масштабе скрываются подписи, кроме выбранного узла, и ослабляются рёбра.

В demand mode `POST /api/graph/query` принимает `revision`, `documents: {knowledge, bookmarks}`, фильтры и `mode: view|candidates|export`. Обычный ответ — до 250 коротких узлов, кандидаты — до 50 доступных для записи; поиск выполняется по всему разрешённому множеству, не только по первой выдаче. Локальная панель связей тоже ограничена 250 узлами. Сервер проверяет актуальную роль и обе document revisions вместе с core revision (409 при изменении). Клиент хранит read models отдельно от `S.data`, ограничивает кэш шестью контекстами и параллелизм четырьмя запросами, отбрасывает устаревшие ответы и обновляет вид после подтверждённого сохранения. Полные записи файлов разрешаются только при открытии/изменении конкретных endpoints. Режим `export` намеренно возвращает весь компактный отфильтрованный граф; это отдельная явная операция. Никогда не сохраняйте короткий узел вместо записи файла.

Фоновые ответы каталога/графа используют `background-render.js`: замена DOM откладывается до завершения pointerup/click, иначе Firefox может потерять клик по заменяемой кнопке. Проверки безопасности/выход не откладываются этим механизмом. Начальные независимые запросы после проверки пользователя выполняются через `loadWorkspaceResources` параллельно; перед применением проверяется поколение сессии. Auth config, Google sign-in и GET preferences читают metadata root, не полные записи файлов. Общие записи/копии и некоторые служебные проверки экспортов пока сохраняют aggregate loader.

### 1.9. Резервные копии и восстановление

Обычные Drive backups сохраняют JSON-снимок и защищают referenced files от garbage collection. Независимый recovery export (`/api/recovery/export`) содержит workspace data, trash references, attachments и SHA-256 checksums. Восстановление локально:

```powershell
node scripts/restore-recovery.js ./smena-recovery-YYYY-MM-DD.json ./.data/recovery-drill-YYYY-MM-DD
```

Скрипт проверяет checksums, требует новый пустой каталог, не изменяет live workspace и восстанавливает `workspace.json` вместе с `uploads/`. Физическое удаление вложений отложено минимум на 30 дней и запрещено, пока файл нужен активной записи, корзине или retained backup.

## 2. English version

### 2.1. Project purpose

Smena Manager is a collaborative team workspace for tasks, projects, teams, calendar, timeline, inbox, notifications, files, knowledge notes, bookmarks, and a graph connecting all permitted materials.

Production: **https://smena-manager.vercel.app/**.

The project follows the KMS-brain-style approach and intentionally does not use PostgreSQL. Shared JSON documents live in Google Drive; binary attachments are separate Drive objects. This is appropriate for a small team and avoids maintaining a separate database service.

Russian and English are supported. Stable English strings are used internally and translated by `src/core/i18n.js`. User-authored titles, descriptions, tags, team names, folder names, and other content must never be translated as UI labels.

### 2.2. Stack and repository map

The frontend is plain JavaScript ES modules, HTML templates, and CSS, bundled by Vite. The backend is Express (`src/server/app.js`), exposed locally through Node and on Vercel through `api/index.js`. Google Drive provides production storage, Redis optionally provides a distributed write lock, Cytoscape renders the graph, PDF.js renders bounded local previews, and Web Push/Gmail deliver notifications.

Node.js **22.x** is required. The most important directories are:

```text
src/core/                  client state, API, i18n, theme, auth, sync, push, search
src/actions/               UI actions and event handlers
src/pages/                 route-level page renderers
src/views/                 task/project/calendar/file/timeline views
src/ui/                    reusable relation panels and helpers
src/shared/                schema, ACL, merge, graph, relations, portable formats
src/features/              graph/archive/subtask/team features
src/server/                Express routes, sessions, Drive, Redis, backups, files, notifications
src/styles/                tokens, shell, responsive and page/view styles
api/index.js               Vercel function entrypoint
scripts/                   setup, deployment checks and recovery tools
tests/server/              server/shared regression suite
tests/e2e/                 Playwright browser checks
docs/                      durable project context and audit notes
```

### 2.3. Data and storage model

The canonical workspace is a versioned JSON snapshot. Core data contains projects, tasks, members, teams, events, notifications, files, relations, and trash. Knowledge notes/folders and bookmarks/folders are independently revisioned logical documents.

In schema v3, core, knowledge and bookmarks remain in the main Google Drive JSON; the full file catalog is stored in immutable project parts with pointers and a compact index in the root. One conditional root ETag write publishes the transaction atomically. Legacy schema-v2 aggregates and separate document files remain readable for migration; separate documents are not the source of truth after the first aggregate write.

Limits and invariants:

- each logical JSON document has a 4 MiB transport budget;
- binary uploads default to 100 MiB;
- Vercel ephemeral storage is never the database;
- localStorage/IndexedDB is an offline cache and draft journal, not shared truth;
- upload bodies are sent to Drive through validated resumable sessions.

### 2.4. Authentication, authorization, and security

Google Sign-In accepts a verified email only when it exactly matches an active whitelist profile from `ACCESS_IDS_JSON`. Signed seven-day sessions use `SESSION_SECRET` and HttpOnly cookies. Access ID login is a local/emergency fallback and is disabled on Vercel by default.

Roles are `admin`, `editor`, and `viewer`. Admins manage membership, settings, backups, and all shared data. Editors can update permitted tasks, projects, files, knowledge, bookmarks, and relations but cannot change membership or workspace settings. Viewers can read shared content and save personal settings only.

ACL checks run on both client and server. The server does not trust role/member/email fields supplied by the client. Session account context is checked against `X-Smena-Account`. Private project endpoints and edges are filtered from API projections and the graph. CSP, security headers, rate limiting, request IDs, strict schema validation, HTML sanitization, and provider-safe logging are part of the security model.

### 2.5. Synchronization and race protection

`src/core/workspace-sync.js` tracks confirmed data, pending drafts, active writes, revisions, retries, and conflicts. `src/shared/workspace-documents.js` provides `serializeWorkspaceWrite`, which serializes writes across the core, knowledge, and bookmark documents that share the Drive aggregate.

Every write uses an expected revision. The server rejects stale writes with `409 REVISION_CONFLICT`; it never silently overwrites newer data. Redis locking is preferred for high concurrency, while direct Drive mode relies on a local queue plus ETag conditional writes. Conflict recovery preserves the local draft and requires an explicit user choice; it does not perform a silent overwrite.

When changing shared state, test rapid sequential edits, reload, two tabs, and stale revisions. Do not introduce fire-and-forget writes outside the serialization queue.

### 2.6. Features

- Tasks/projects: list, board, table, calendar, timeline, assignees, priorities, due dates, recurrence, subtasks, dependencies, milestones, comments, reactions, mentions, and attachments.
- Inbox/notifications: recipient-scoped mentions, assignments, comments, deadlines, outbox, independent email/push delivery, retries, cleanup, and read state.
- Files: resumable Drive uploads, stable physical identity, safe previews for bounded images/text/PDF, downloads for unsupported formats, delayed physical deletion.

Workspace/project uploads use a real keyboard-operable button (`chooseStoredFiles`), not only a hidden-input label. Mobile list cards use full-width detail rows, localized labels and a menu beside the filename. File search includes both source and localized type names; result counts, query clearing and filter reset are visible with restored search focus. The mobile toolbar uses two filter columns; a container query also accounts for the width remaining beside navigation. Server permission checks remain authoritative; these UI operations do not change physical storage identity.

Files also have logical project folders (`project.fileFolders`) with nesting, search, breadcrumbs, bounded pages and a recoverable empty-folder archive. `file.folderId` and the matching task attachment reference only an active folder in the same project. Current-folder uploads carry folderId through both proxy upload and signed direct-upload tickets. Moves never change storage identity, physical Drive location or ACLs. Limits: 2000 folders per project, depth 32, names 1–120 characters, unique active sibling names. A trashed file whose original folder is unavailable restores at the project root.

Uploading, renaming, organizing folders and moving files require project edit access. Removing someone else's file additionally requires an administrator role; view/comment users get no file write actions. Grid/list selection persists across filters, is scoped to the user/workspace and is capped at 500 files. Moves stay within one project; bulk removal uses recoverable trash, a filename confirmation and Undo. The complete batch is revalidated before any mutation; task attachments update by stable ID. Folder pages show 4 items on mobile/8 on wider screens; the destination picker shows searchable pages of 20. This organizes application files, not arbitrary contents of the entire Google Drive account.

File search and folder counters share `createFileIndex` built from the current snapshot, without a cache that could outlive sync or ACL changes. Queries match multiple words, ignore case and treat Russian е/ё equally. Grid/list, sorting, 25/50/100 files per page, folder density and collapsed state persist in device-local `smena.files.ui.v1`, scoped to the account/workspace pair. Current queries/selection do not persist automatically; users can explicitly save up to 12 named filter presets under the separate `:filters` key on this device. Presets include project, folder, query, type, sort and recursive mode; unavailable destinations are not silently replaced with a global view. Compact folders page at 8 mobile/16 wider items; tiles remain at 4/8. File/folder page number inputs submit with Enter.

Workspace and project files share `pageFiles(projectId)`; project context locks the data scope and upload targets. Actions/dialogs load with the lazy page, including direct project-tab entry. Folder relocation previews affected folder/file counts and validates cycles, depth, sibling collisions and ACLs before changing anything. A tree stays in its project; file folder IDs and storage identity remain unchanged. Folder results are direct by default, with explicit Include subfolders. Select page and Select results are distinct; selecting the whole result is disabled above 500 files.

The client requests `X-Smena-File-Catalog: demand`: the initial core snapshot neither includes the complete file array nor fetches catalog pages. POST `/api/files/catalog/query` returns 25/50/100 IDs, exact totals, up to 32 requested folder counts and up to 500 result IDs for explicit bulk selection. POST `/api/files/catalog/resolve` resolves at most 100 IDs per request with revision/ACL checks and a 2 MiB page budget; the client follows continuation pages for large records. `D().files` contains only needed records and selection. PUTs send `fileChanges`: cache eviction is not deletion, new file-trash commands corroborate explicit removals, and the server completes task/project cascades with full file records in recoverable trash. File deep links, uploads, attachments, search and related endpoints resolve identities on demand. Catalog capacity is 32 MiB, core/documents remain 4 MiB; task attachment/trash metadata still count toward core. Legacy `pages` transport remains supported.

Bulk download builds a browser-local ZIP from explicit selection, capped at 100 stored files and 50 MiB source bytes (independent of the 500-file move/trash selection limit). `file-download.js` and `fflate` load on demand. Content is fetched sequentially through the existing authorized `/api/files/:id/content` endpoint; no server-side archive, temporary Drive folder or third-party ZIP service is used. `ZipPassThrough` avoids redundant recompression of already-compressed formats. Project/folder paths and Unicode are preserved; case-insensitive collisions, unsafe paths and reserved filenames are sanitized only in the export, never by renaming originals. Progress/cancellation are available. Any failed read, actual-size overflow or account/workspace change discards the whole result. Legacy records without stored content must be deselected. Budgets are enforced before fetching and during stream reads, including a zero-byte remaining budget. Proxy uploads preserve UTF-8 filenames independently of legacy Latin-1 multipart decoding.

A separate Stream ZIP action uses a same-origin form POST to `/api/files/archive?account=...`, the HttpOnly cookie and account binding. Native browser downloading does not replace the workspace page; application progress belongs to browser-local ZIP only. The server uses `ZipPassThrough`, chunks up to 64 KiB and backpressure, never a whole-file/archive buffer. Limits: 500 files, 250 MiB actual source bytes and 45 seconds (function configured at 60). Each next file rechecks current role/membership/project/storage identity. Disconnects/timeouts destroy the stream; no archive is retained in Drive. Expiring concurrency leases are instance-local: one per account, eight overall, not a distributed quota or resumable job. Physical iOS/Android background/lock-screen download behavior remains unverified.

Prepared browser ZIPs retain an explicit Save ZIP link for up to five minutes: browsers may suppress repeated automatic downloads after asynchronous preparation. Retrying this link does not reread Drive. Blob URLs are revoked on dismissal, replacement, expiry or invalid account/workspace/ACL context. Do not treat an automatic link click as proof of delivery; inspect the downloaded archive. A ready result does not block starting another export.

Resumable exports use the separate `/api/files/exports` protocol: hidden jobs persist in the Drive aggregate and immutable 4 MiB parts are Drive files. Limits: 500 files/1 GiB, 24-hour expiry, 16 live jobs overall/four per user, four active worker leases and one unfinished export per user. Revision/ETag checks and fencing tokens prevent stale workers from publishing checkpoints. Staging is persisted before uploading; unknown upload outcomes are found by name and SHA-256-verified before reuse. Source versions, sizes, current ACLs, part SHA-256 and ZIP CRC are checked. Ready results stream with deterministic ETags/HTTP byte ranges, without buffering the complete ZIP. Preparation advances through an active tab; closing/backgrounding pauses it until resumed, not an autonomous queue. Job metadata has a separate 8 MiB cap; parts use the normal registry/deferred GC, protected by live jobs.

Google Drive stores a schema-3 root with a v3 `_fileCatalog` manifest plus immutable project JSON parts (up to 2,000 records/2 MiB). The manifest has part IDs, SHA-256, sizes and a compact identity/folder/size/task index, not complete file records. Auth/core read the root without parts; project/identity reads determine readable projects before fetching relevant parts. Global sort/search scans readable parts server-side and returns bounded client pages. Search projections discard history/storage fields after validating original records; a checksum-verified immutable-part LRU has an 8 MiB UTF-8 byte budget. Cold global queries still scan readable parts. Whole-workspace writes/backups materialize all records for existing validation and atomic revisions, but graph/picker loading uses bounded read models described below. Parts are verified and unchanged parts reused; the root is published last using If-Match. Initial cutover creates a full backup. Aggregate/v1/v2 remain readable; unsupported schemas/manifests fail closed for older server writers. Operator-only `node scripts/file-catalog-layout.js --inspect` is read-only. Layout changes need `--layout=aggregate|project-shards --revision=N --confirm`, back up the latest state and retain schema 3/newer edits. Never replay the migration backup as rollback. Superseded/unpublished parts are not automatically collected yet. Data transfer shows the actual layout/part count; independent capacities and worker-local counters remain. Presets stay device-local; app updates require an explicit action after saved-state/form/transfer checks. Record order lives in the manifest; part content is sorted by stable file ID so global reordering does not rewrite other projects. Reads recheck current membership/role; content download resolves only the requested file.

**Cold-search update — 24 October 2026.** Manifest v3 now supports a derived `part.search: {version: 1, id, sha256, bytes}` descriptor. Search parts contain only `fileCatalogIndex`, not histories/physical storage identities; canonical parts already containing only these fields share the same bytes/ID. Search/graph readers verify checksums, sizes, order, project and root identity/folder/size/task keys. Fresh ACL checks precede part reads and cannot be bypassed by the immutable cache. This is a metadata index, not an inverted full-text index: cold global queries still scan readable compact parts. Missing descriptors retain the verified canonical fallback. Index publication accompanies the next normal root write; reads never silently migrate storage. History-only changes reuse an unchanged index. Older v3 writers may drop the derived pointer without losing canonical files.

Ancillary reads: resumable-export list/result/validation resolve only live owned job IDs from the same root; no such jobs means no part reads. Native streamed ZIP resolves selected identities and rechecks each required file before transmission. Size/version/storage identity and current-role checks remain enforced. Full materialization also uses the verified LRU. Knowledge search, outbox diagnostics and push/test member resolution skip catalog parts; GET preferences reuses its own private auth-middleware snapshot and returns only the current member's settings. Read models must never become writable workspace snapshots. Whole-workspace mutations and backup/restore still materialize every file.

Detailed capacity uses optional `_fileCatalog.accounting` v1: revision, exact UTF-8 `{data:{files},revision}` envelope bytes and `fileStorageAccounting` calculated from complete data. Every normal write recomputes it, including trash/GC/registry-only changes; the conditional root write publishes it atomically with part pointers. `loadDatabaseStatus` refreshes the root, validates shape/revision/counters, downloads no parts and does not even allocate catalog identity rows. Status never replaces the canonical write baseline; layout, document projections and capacities share the same root. `/api/storage/status` exposes `catalogAccounting: {source: 'manifest'|'canonical', revision}`. Legacy roots without summaries use exact canonical fallback; reads do not migrate storage. Invalid/unsupported summaries fail explicitly rather than reporting zeroes. Status does not reuse a stale worker database. Aliases, unknown sizes and retained physical objects preserve previous semantics; backup-only bytes remain `null`, not complete Drive accounting. UI unknown counts are separate for logical, active and retained categories, never a sum of overlapping populations. Root size and manifest validation still grow with the catalog; the summary does not remove those constraints.

`getWorkspaceDatabase({fields})` passes `identities: false` to `loadDatabaseCore` when files are not requested: authorization/ancillary projections allocate no file stubs. Ordinary core and explicit file projections retain the ID index. Root-only accounting is not a fresh existence/checksum scan of every part or binary object; actual reads and recovery operations retain those checks.

Core saves with `fileChanges` reconstruct the readable catalog, complete cascades and enforce ACLs inside `mutateWorkspaceDatabase` against one canonical snapshot, with no separate full preload. Import, restore and workspace deletion use that same complete snapshot for their safety backup rather than reloading it. The internal mutation option `backupLabel` creates a checkpoint after validation and before CAS publication; backup failure stops publication, and Redis ownership is checked again afterward. Imports record their checkpoint ID in history. Standalone Vercel backups always refresh canonical storage instead of reusing the two-second UI cache. These operations still require complete canonical validation and complete backup documents/files.

Only the selected document plus its independent revision, or the acting member's profile/preferences/read-state fields, may change. Files, tasks, projects, ACLs, relations, registry, trash, GC and sibling documents stay unchanged. The existing local queue/Redis lock, ownership check and snapshot-specific If-Match still apply. Core/document budgets are checked normally; exact catalog bytes are rebased from revision-bound accounting for revision digit growth, preserving physical counters and part pointers. Preferences return identity rows solely for existing ACL projection and demand hydration; the global canonical cache is invalidated, never populated with a partial snapshot. Legacy roots, absent accounting and migration side effects fall back to the full path; corrupt manifests/accounting and missing ETags fail closed. Legacy preference clients retain complete responses. This is narrowly scoped root copy-on-write, **not** independent project transactions: latent corruption of unchanged parts is not rescanned by metadata writes; SHA-256 and identities are verified on actual reads, while backup/restore and file mutations materialize the complete catalog.

Allowed fields are name/folderId and decorative-file type without physical identity. `loadDatabaseFilePatch` privately binds the snapshot to its root/ETag/verified rows; `saveDatabaseFilePatch` preserves untouched pointers, global order, registry/retention/physical accounting and recalculates exact catalogBytes. Growing parts split through the existing writer. Ownership is checked during staging and immediately before root CAS; partial snapshots never enter the complete worker cache. Mixed core mutations, additions/removals/duplicates, physical changes and migrations retain canonical fallback. Unchanged parts are not rescanned: this is neither a complete Drive integrity scan nor independent project transactions.

Backup update: standalone copies always read a fresh root, but `loadDatabaseForBackup` can confirm the exact ETag of an already complete canonical worker snapshot and skip rereading parts. The pre-await captured snapshot is used, never a subsequently replaced global variable. Missing/mismatched ETags, cold workers or changed roots require full materialization and checksum verification. Backups remain standalone complete JSON with histories/registry; `backupJson` emits arrays record by record without another catalog-sized JSON string. Binary uploads remain separate objects: ordinary JSON backups are not independent attachment-byte archives. Legacy aggregate storage remains supported. Earlier statements requiring complete rereads for all file changes/standalone backups describe general fallback, not these narrow exceptions.

Committed `mutate` commands call `flushLocalSave` immediately after permission guarding rather than waiting for the 150 ms input debounce; ordinary form input still coalesces. The E2E persistence check waits for the PUT acknowledgement containing the specific task, then reloads. The responsive sweep is split into four independent viewport tests with the existing 360-second per-test bound and the same 140 route/viewport pairs. `workspace-smoke.spec.js` records video/DOM traces on the first retry, retains failure screenshots, and supports a full first-run trace via `--trace retain-on-failure`. Recording options belong at file scope, not inside `describe` (Playwright worker-scoped options).

Data transfer keeps primary limits visible and places technical accounting behind “Storage details”. Settings navigation is horizontal up to 1100 px, revealing the selected section after both rendering and resizing. System backup labels are localized without renaming Drive objects; custom labels are preserved. Manual backups are not removed automatically; restoring does not delete the selected checkpoint.

- Knowledge: Markdown notes, folders, tags, categories, summaries, stable `[[wiki links]]`, explicit resolution for ambiguous targets.

- Graph: typed node keys (`note:<id>`, `bookmark:<id>`, `file:<id>`, `project:<id>`, `task:<id>`), manual relation tombstones, computed associations, wiki links, filters, search, connected-only, archive, depth 1/2, selection, local graphs, JSON export, and accessible list mode.

### 2.7. API and operations

Public endpoints include `/api/health`, `/api/auth/config`, `/api/auth/google`, and `/api/auth/validate`. Authenticated endpoints cover workspace/core and document snapshots, revision/status, sessions, preferences, files, backups, recovery export, push subscriptions, notification delivery, and the protected cron routes.

`GET /api/health` is only liveness. Cron HTTP 200 is only transport success; operational success requires the returned status, storage, backup, outbox, coordination, and delivery diagnostics to be healthy. Admin readiness is exposed by `/api/readiness`.

Daily Vercel cron is `0 4 * * *` UTC, equivalent to 08:00 Europe/Saratov. It queues reminders and email digests, cleans notifications and abandoned uploads, runs retention cleanup, creates the automatic backup, and retries the outbox.

### 2.8. Recovery and local workflow

The independent recovery export contains workspace data, retained trash references, attachments, and SHA-256 checksums. Restore into a new empty directory with:

```powershell
node scripts/restore-recovery.js ./smena-recovery-YYYY-MM-DD.json ./.data/recovery-drill-YYYY-MM-DD
```

The command verifies checksums and never changes the live workspace. Physical attachments are retained for at least 30 days and while referenced by live records, trash, or retained backups.

Common commands:

```powershell
npm install
npm run dev
npm run build
npm run preview
npm run lint
npm run format:check
npm run test:server
npm run test:e2e
npm run check:deploy
npm run check:live
```

Local data belongs in `.data/`. Never commit `.env`, access IDs, cookies, refresh tokens, private keys, full Drive payloads, or production exports. Use `npm run setup:storage` only from one controlled maintenance process and `npm run setup:gmail` for the separate Gmail consent flow.

### 2.9. Engineering rules for future agents

Read the relevant tests and shared schema before editing. Keep ACL, revision checks, document serialization, and user-content escaping intact. For UI work, update both locales, verify 320/390/768/1024/1440 px where relevant, and avoid translating user-authored content. Run lint, server tests, build, and focused browser checks. If a code change is made, create a focused commit and push it according to the repository workflow. Report changed files, verification commands, commit, deployment status, and any unverified production assumptions.

The durable handoff prompt should state the goal, scope (local or production), whether cloud mutations are authorized, whether implementation is requested or only an audit, whether commit/push is required, and which team data must remain untouched.

### 2.10. Known limitations

The JSON snapshot model and 4 MiB document budget are not a replacement for an entity-oriented database at larger scale. The graph's 250-node canvas limit is intentional; use filters, local graphs, export, or list mode for larger workspaces. The initial bundle still has a size warning even though graph and PDF code are lazy-loaded. Production acceptance requires authenticated checks; public liveness cannot prove Drive writes, notification delivery, or recovery. Gmail, push, scheduled cron, and attachment recovery require independent acceptance evidence.
