# Раздельное хранение заметок — U01–U03

## Что реализовано

Google Drive остаётся основным хранилищем. В корневом документе остаются каталог заметок, папки, права и указатели. Тексты и исторические версии сохраняются отдельными неизменяемыми объектами, проверяемыми по SHA-256, размеру и ID заметки. Чтение выбранного текста не требует чтения остальных заметок или каталога файлов. Удаление в корзину и возврат сохраняют указатели; самостоятельные экспорты и резервные копии раскрывают тексты, чтобы восстановление не зависело от исходных объектов.

Производный поисковый индекс разбит на сжатые части, связанные с версиями тел. Изменение текста обновляет затронутую часть; смена папки или названия не перечитывает все тексты. Холодный поиск читает подходящие части индекса, а не исходные тела и историю. Он ещё не является позиционным обратным индексом: запрос по всему большому пространству может прочитать несколько частей, поэтому производительность реального Drive нужно измерить отдельно. Ошибка/отсутствие индекса показывается явно, а не как ноль совпадений.

Очередь TXT/MD проверяет файлы последовательно, затем сохраняет по одному. Лимиты выбора: **1 000 файлов, 256 MiB всего, 2 MiB на исходный файл**, и менее 4 MiB на JSON-запрос после декодирования. Большой общий объём больше не нужно помещать в один запрос. Уже принятый файл и подтверждение его импорта публикуются одной записью корня. Повтор после потери ответа не создаёт вторую заметку. Журнал принадлежит пользователю и пространству; право записи перепроверяется при каждом запросе.

## Включение на сервере

По умолчанию `KNOWLEDGE_CATALOG_ENABLED=false`. Локальная приёмка выполнена с `true` на отдельном синтетическом стенде; production пока отвечает 402. Значение не включено автоматически на рабочем Google Drive.

1. Восстановить доступность Vercel либо развернуть подготовленный VPS. Проверить, что записывает только согласованный backend, а Google OAuth/Drive и создание самостоятельной копии работают.
2. Установить релиз с поддержкой нового протокола на backend и frontend. В серверном окружении задать `KNOWLEDGE_CATALOG_ENABLED=true`, перезапустить/переразвернуть приложение и обновить открытые вкладки пользователей. Секреты не меняются и не переносятся в Git.
3. Под владельцем открыть **База знаний → Инструменты → Хранение базы знаний**. Проверить расчёт активных заметок/корзины, размер и наличие некорректных объектов. Согласовать короткую паузу командного редактирования. До первого окна создаётся свежая самостоятельная копия; без неё перенос не запускается.
4. Подтвердить расчёт и запустить перенос. Каждое окно из трёх заметок публикуется с проверкой ревизии. Закрытие/пауза прекращают следующие запросы; продолжение доступно в том же окне. Повторный запуск после завершения должен показать ноль оставшихся объектов. Старые уже вынесенные тела также получают превью и индекс.
5. В отдельном тестовом пространстве проверить чтение, правку/reload, восстановление версии, корзину/возврат, TXT/MD-очередь с паузой/reload, поиск дальнего фрагмента текста и самостоятельный экспорт/восстановление. Повторить RU/EN, обычного участника и гостя. Не считать HTTP 200 доказательством правильного содержимого.

## Продолжение импорта

Открыть **Инструменты → Очередь импорта**, выбрать незавершённую очередь, повторно выбрать ожидающие исходные файлы и нажать «Продолжить импорт». Имена, размер и hash текста должны совпасть. Уже сохранённые файлы повторно выбирать не требуется. Тексты не хранятся в localStorage; без исходников продолжить непереданные файлы нельзя. Закрытие окна не отменяет уже сохранённые заметки; остановка импорта также их сохраняет. Ошибочные файлы исключаются при предварительной проверке.

## Откат и ограничения

- Откат релиза должен сохранять поддержку внешних тел/истории. Простое выключение флага не возвращает старый формат и не удаляет объекты. Старый монолитный PUT защищён от перезаписи непрочитанных тел.
- Данные возвращаются только штатным восстановлением проверенной самостоятельной копии с отдельным согласованием; откат кода не равен откату данных.
- Не удалять объекты тела/истории/индекса вручную. Контролируемая очистка с анализом достижимости и срока хранения — отдельный незавершённый этап U11.
- Начальный backup новой очереди пока синхронный. На большом холодном Drive он может упереться во время запроса: отдельная фоновая подготовка копии входит в следующий аудит.
- Каталог метаданных и журнал ограничены размером корня. Введение отдельных тел не обещает неограниченного количества заметок.
- Без сети поиск явно ограничен уже скачанными заметками. Сохранённые источники/результаты не должны переходить между аккаунтами и пространствами.
- Настоящие Google Drive/OAuth, восстановление в production, Safari/WebKit и реальные телефоны этим локальным проходом не приняты.

## English handoff

U01–U03 retain Google Drive as authoritative storage. Metadata, immutable hash-checked current bodies, historical snapshots and compressed derived search parts are separate. Membership precedes search/read results and is rechecked under every import write lock. Catalog/body hydration is not treated as an edit. Standalone exports/backups expand referenced content.

The gate defaults to `false`; enable it only with a compatible frontend/backend release and a reviewed, backed-up migration through Library tools → Knowledge storage. Migration commits three notes per window and can pause/resume. Existing external bodies without previews/index coverage are included. Production is currently unavailable (402), so no real team migration was performed.

Resumable TXT/MD import accepts up to 1,000 files / 256 MiB per selection, 2 MiB per source and a bounded single-file JSON request. Review retains metadata and File handles, not a combined payload. A server-owned per-user/workspace journal atomically records accepted notes and receipts. Reselect pending originals after reload; source hashes prevent accidental substitution. Accepted files survive pause/cancel and retry without duplication.

Outstanding boundaries: cold search scans compressed derived parts rather than positional postings; metadata root size remains finite; initial import backup is synchronous; reference-aware garbage collection is not implemented; real Drive latency, production restore and physical mobile/WebKit acceptance are pending. Do not delete immutable objects or treat disabling the gate as data rollback.

## Метаданные (N02, локальная приёмка)

`KNOWLEDGE_METADATA_SHARDS_ENABLED=false` — отдельный выключенный по умолчанию gate. Первое включение требует `KNOWLEDGE_CATALOG_ENABLED=true`, свежей независимой копии и согласованного обновления backend. Изменения каталога публикуют неизменяемые части по SHA-256 перед атомарной заменой корня. Заметки, папки, импортные журналы и описание индекса вынесены из корня; идентификаторы и порядок остаются в корне. Частичное чтение для файлов не является полным документом и не допускается к замене знаний. Права проверяются до чтения выбранных частей.

Сырой корень имеет schemaVersion 4, логическая модель — 3. Откат на старый backend без поддержки v4 запрещён: он должен отклонить формат, а не принять идентификаторы за пустые заметки. Выключение gate после миграции не уплощает данные; нужен релиз с поддержкой чтения v4. Отсутствующая/повреждённая часть даёт явную 503 и не инициализирует пустую базу. Незавершённая публикация оставляет старый корень действующим; оставшиеся объекты нельзя удалять без расчёта достижимости.

Локальный лимит логического документа знаний 64 MiB не расширяет HTTP-лимит 4 MiB. Пакетный транспорт и дельты — отдельный шаг N02; не включать gate в production до его приёмки. 10 001 метаданных (>4 MiB) прошли round-trip с корнем <512 KiB; это synthetic-проверка, не замер Google Drive.

Metadata sharding is a separate default-off gate. It publishes immutable verified parts before the CAS root; old servers must fail closed on raw schema v4. Missing parts are errors, never empty initialization. Keep a compatible server for rollback; turning the gate off does not flatten migrated storage. Local 10,001-row checks do not constitute live migration acceptance.
