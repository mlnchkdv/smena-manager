Важные особенности текущей реализации:
- Node.js: major 22, установленный с актуальными исправлениями безопасности.
- Фронтенд собирается Vite в dist/.
- Backend — Express; команда запуска npm run start:server.

- Express сам по себе не раздаёт готовый фронтенд.
- Основное хранилище — Google Drive: JSON-документы, части каталогов,

- Перенос на VPS сам по себе не отменяет программные лимиты документов,
  истории, импорта, экспортов и загрузок.

2. ЦЕЛЕВАЯ СХЕМА

Запускай один экземпляр Node.js через systemd.
Не используй dev-сервер Vite, vite preview, node --watch или PM2 cluster

Наличие REDIS_URL само по себе не означает, что VPS-путь записи стал
безопасным для нескольких процессов. Горизонтальное масштабирование
не входит в эту установку.

3. ПОДГОТОВЬ ПЕРЕНОС ДАННЫХ

Сначала:
- определи существующую корневую папку Drive и закреплённые ID;
- сохрани действующие ID пользователей, пространств, проектов и материалов;
- проверь наличие актуальной восстанавливаемой резервной копии;
- отдельно зафиксируй покрытие бинарных вложений резервированием;
- убедись, что у пользователей нет несинхронизированных изменений;
- подготовь порядок переключения и отката.

Используй существующее хранилище Drive. Не создавай пустое пространство
вместо рабочего и не импортируй поверх него демонстрационные данные.

Не запускай setup:storage вслепую. Для действующего хранилища сначала
проверь закреплённые идентификаторы. Если действительно отсутствуют
служебные объекты, выполни штатный setup однократно из одного процесса.
При неоднозначных совпадениях останови этот шаг и выясни правильные ID,
не удаляя объекты наугад.

В момент переключения оставь только один активный production backend
и один плановый запуск автоматизации. Исключи параллельную рабочую запись
со старого Vercel и нового VPS.

Если Vercel сейчас заблокирован, не меняй тариф и не совершай платежи.
Зафиксируй, что перед его возможным восстановлением старые задания
и доступ на запись должны быть отключены или согласованы.

- Используй проверенные официальные источники.
- Создай непривилегированного пользователя для приложения.
- Сохрани рабочий SSH-доступ перед изменением firewall.
- Разреши входящие HTTP/HTTPS и нужный SSH-порт.
- Не публикуй порт 3001 и служебные хранилища наружу.
- Проверь время, синхронизацию часов, свободные RAM, диск и /tmp.
- Проверь исходящий HTTPS-доступ к Google OAuth, Drive, Gmail API

Предлагаемая структура:
- /srv/smena-manager/releases/<COMMIT>/ — отдельные релизы;

Секретные файлы должны находиться вне Git и web-root, иметь ограниченные

7. НАСТРОЙ SYSTEMD И NGINX

Создай systemd unit:
- непривилегированный пользователь;
- WorkingDirectory активного релиза;
- EnvironmentFile с защищённым окружением;
- запуск node src/server/index.js;
- проверка конфигурации перед запуском;
- автоматический перезапуск при сбое;
- автозапуск после перезагрузки;
- логи через journald;
- доступ на запись только к действительно необходимым каталогам.

В Nginx:
- направляй /api и /api/* на 127.0.0.1:3001 с сохранением исходного URI;
- не используй Vercel-rewrite через __smena_path;
- для маршрутов SPA используй fallback на index.html;
- для отсутствующих JS/CSS/assets возвращай 404, а не index.html;
- отключи кеширование API, index.html, sw.js, app-version.json
  и offline-assets.json;
- используй длительный кеш только для файлов с хешем в имени;
- сохрани доступность ассетов предыдущего релиза для открытых сессий;
- настрой таймауты и ограничения запросов с учётом кода приложения;
- сохрани передачу Cookie, Authorization, Origin и X-Smena-* заголовков;
- проверь скачивание, потоковые ответы и Range-запросы.

Настрой HTTPS, перенаправление HTTP→HTTPS и автопродление сертификата.
Проверь nginx -t и тест продления сертификата.

Перенеси согласованные security headers из src/shared/http-security.js.
vercel.json на Nginx автоматически не применяется.
Сохрани Google-совместимый COOP same-origin-allow-popups.
Не ослабляй CSP до произвольных script-src unsafe-inline.

Отдельно проверь определение IP клиента:
сейчас non-Vercel login limiter использует socket.remoteAddress.
За Nginx это может объединить всех пользователей в один лимит.
При необходимости сделай небольшую проверенную адаптацию:
доверять только локальному reverse proxy, использовать корректный
клиентский IP и исключить подделку X-Forwarded-For извне.
Одного app.set('trust proxy', ...) недостаточно, если функция limiter
продолжает брать socket.remoteAddress первой.

8. НАСТРОЙ GOOGLE-ВХОД И УВЕДОМЛЕНИЯ

Добавь https://<APP_DOMAIN> в Authorized JavaScript origins существующего
Web OAuth-клиента. При использовании www добавь его origin отдельно.
Сохрани origins других работающих приложений, включая KMS-brain.

Текущий Google-вход использует GIS popup и POST /api/auth/google.
Не придумывай отсутствующий /api/auth/callback и не требуй redirect URI
для popup-входа.

Gmail consent — отдельный поток. Если действующий refresh token работает,
не заменяй его. При необходимости повторного consent используй штатный
setup:gmail с правильным redirect URI на компьютере оператора
или через корректно организованный туннель.

APP_ORIGIN должен указывать на новый HTTPS-домен, чтобы ссылки
в письмах и уведомлениях не вели на Vercel.

Смена домена не переносит автоматически cookies, localStorage,
офлайн-черновики, разрешения уведомлений и push-подписки браузера.
На новом домене пользователю потребуется вход и повторное подключение push.
Не выдавай это за сброс уже созданной сессии на новом домене.

9. ЗАМЕНИ VERCEL CRON

На VPS vercel.json не запускает задания.

Создай systemd oneshot service и timer для обращения к существующему
GET /api/cron/reminders через loopback с Authorization: Bearer CRON_SECRET.

Базовое расписание текущего vercel.json:
04:00 UTC ежедневно = 08:00 Europe/Saratov.

Укажи часовой пояс явно и проверь расписание через systemd-analyze calendar.
Предусмотри Persistent=true, защиту от одновременных запусков,
ограничение времени выполнения и журнал результатов.

Не передавай cron-секрет в URL, аргументах процесса или логах.
Используй защищённое окружение/файл и небольшой helper.

HTTP 200 не считается подтверждением успешного выполнения:
helper должен проверить JSON status и результаты всех workspaces.
degraded/failed должны отражаться как проблема мониторинга.
Не запускай повторно весь cron автоматически после частичного успеха.

Не используй /api/cron/reminders как обычный smoke-check:
он создаёт копии, обрабатывает уведомления и выполняет обслуживание
по действующим политикам.

Активируй production-таймер после проверки конфигурации и исключения
дублирующего запуска со старого хостинга.
